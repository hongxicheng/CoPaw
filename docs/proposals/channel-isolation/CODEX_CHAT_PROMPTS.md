# Channel 隔离重构 Codex Chat 使用指南

## 1. 文档职责

本文档只提供实施、修复、审查和 Gate 验收的工作流程与提示词模板，不定义或复制
Channel 隔离的架构决策。

三份文档的职责固定为：

| 文档 | 唯一职责 |
| --- | --- |
| `DESIGN.md` | 架构、协议、职责、兼容性和 ADR 的唯一事实来源 |
| `IMPLEMENTATION_WORK_PLAN.md` | 任务拆分、依赖、范围、产物、验收、Gate 和进度 |
| `CODEX_CHAT_PROMPTS.md` | Chat 工作方式和通用模板 |

Prompt 不得重新定义 Design 中的决策，也不得给某个任务增加 Plan 中不存在的验收要求。
架构变化必须先更新 Design 和 ADR，再同步调整 Plan；不能通过修改提示词静默改变设计。

## 2. 每个 Chat 读取什么

每个 Chat 只处理一个明确边界：一个 `CH-X-XXX` 任务、一组已确认的同任务审查问题，
或一个 `Gx` Gate。

开始前按当前范围读取：

1. `AGENTS.md`；
2. `IMPLEMENTATION_WORK_PLAN.md` 中当前任务、直接依赖和所属 Gate；
3. `DESIGN.md` 中与当前任务直接相关的章节和 ADR；
4. 当前任务涉及 Channel 开发、迁移或审查时，读取
   `.codex/skills/channel-development/SKILL.md`；
5. 当前代码和测试，用于确认事实和回归基线。

不要求每个 Chat 重新分析所有 Channel 或所有阶段。实施 Chat 如果发现必须修改未纳入
当前任务的架构、任务依赖或验收条件，应停止实施并说明，不得自行扩大范围。

资料优先级为：

1. `DESIGN.md` 的相关架构决策和 ADR；
2. `IMPLEMENTATION_WORK_PLAN.md` 的任务范围、依赖和验收条件；
3. `AGENTS.md` 和适用 Skill 的工程规范；
4. 当前代码和测试所证明的现状。

如果 Design 与 Plan 冲突，修改前必须报告冲突并等待用户决策。

## 3. 标准任务流程

一个任务使用一个实施 Chat，并按以下顺序推进：

1. 只读检查当前任务，提出改动方案、验证方法和 checklist。
2. 用户确认方案后才修改文件。
3. 只实施当前任务，运行与风险匹配的测试和检查。
4. 按用户授权创建只包含当前任务的提交。
5. 使用独立 Review Chat 审查该任务的完整提交或差异。
6. 将已确认问题交回原实施 Chat 修复并重新验证。
7. Review 和最终验证通过后，按 Plan 更新任务状态。
8. 一个 Gate 的全部前置任务完成后，再进行独立 Gate 验收。

复选框、实施 Chat 的自我结论和已有提交都不能单独作为完成证据。任务必须满足 Plan
中的验收条件；Gate 必须逐项有直接证据。

如果只读检查证明一个任务无法在一个 Chat 中形成完整、可验证、可独立 Review 的产物，
应先提出拆分建议。拆分必须先更新 Plan；不能让多个 Chat 用同一个任务号分别实现一部分。

## 4. 实施 Chat 提示词

将 `<TASK_ID>` 替换为 Plan 中的一个任务编号。

```text
你负责实施 <TASK_ID>，本 Chat 只处理这一个任务。

开始前读取：
1. AGENTS.md
2. IMPLEMENTATION_WORK_PLAN.md 中 <TASK_ID>、直接依赖和所属 Gate
3. DESIGN.md 中与 <TASK_ID> 直接相关的章节和 ADR
4. channel-development Skill（如适用）
5. 当前相关代码和测试

DESIGN.md 是架构决策的唯一事实来源；Plan 只定义本任务范围、依赖和验收。
不得从本提示词推导新的架构要求。

第一步只读检查，不修改文件。先输出并等待我确认：
- 对任务目标和验收条件的理解
- 依赖的 Design 章节和 ADR
- 已确认事实、假设和未知项
- 预计修改或新增的文件
- 最小实施步骤及每一步的验证方法
- 与任务验收条件逐项对应的 checklist
- 明确不在本次范围内的内容

如果 Design、Plan 和当前代码事实冲突，或完成任务必须改变既有架构决策、任务范围、
依赖或 Gate，立即停止并说明，不得自行选择或扩大范围。

我确认方案后再实施。实施时遵守 AGENTS.md 和适用 Skill，只做能够追溯到
<TASK_ID> 的最小改动，不处理无关清理，不覆盖用户已有改动。

完成后：
- 运行与任务风险匹配的测试和检查
- 对照 Plan 中 <TASK_ID> 的每条验收条件给出证据
- 展示修改文件、差异摘要、测试结果和未解决风险
- 按 Plan 的状态规则更新该任务已有的唯一进度记录，不重复追加过程记录
- 只有获得明确提交授权时，才创建只包含 <TASK_ID> 的提交
- 初始提交后任务仍保持等待独立 Review；未经 Review 和最终验证不得标记完成
```

## 5. 审查问题修复提示词

优先把已确认问题交回原实施 Chat。

```text
继续处理 <TASK_ID>，本次只修复以下已确认的审查问题：

<FINDINGS>

开始修改前逐条输出并等待我确认：
- 是否同意以及代码或测试证据
- 是否属于 <TASK_ID> 范围
- 最小修复方案
- 需要新增或调整的测试
- 是否会改变 Design、Plan 或既有 ADR

确认后只修复已接受且属于当前任务的问题。范围外问题只记录，不顺手处理。
修复后重新运行相关测试和检查，给出逐项验证证据，并按用户授权创建独立修复提交。
不要 amend 或改写历史，不要把未完成事项标记为完成。
```

## 6. Review Chat 提示词

使用独立 Chat，并替换 `<TASK_ID>` 和 `<COMMIT_OR_DIFF>`。

```text
只审查 <COMMIT_OR_DIFF> 对 <TASK_ID> 的实现，不修改任何文件。

读取：
1. AGENTS.md
2. Plan 中 <TASK_ID>、直接依赖和所属 Gate
3. Design 中与该任务直接相关的章节和 ADR
4. channel-development Skill（如适用）
5. 当前提交、相关代码和测试

只按 <TASK_ID> 的范围和验收条件审查，不扩展成全仓库 Review。重点检查：
- 是否完整满足任务且没有越界
- 是否违反相关 Design/ADR
- 是否存在可触发的行为回归、竞态、恢复、安全、兼容性或跨平台问题
- 测试是否能证明验收条件，而不只是覆盖实现细节
- 状态记录和完成结论是否有事实依据
- 是否引入无必要的抽象或重复事实来源

按 P0、P1、P2、P3 排序输出问题。每条必须包含：
- 严重级别和标题
- 文件与精确行号
- 可触发场景和实际影响
- 当前测试为何没有拦截
- 最小修复方向

不要报告没有行为影响的纯风格偏好。范围外问题不得阻塞当前任务。
如果没有问题，明确写“未发现问题”，并列出残余风险、未运行测试和仍需 Gate
验证的内容。最后说明该任务是否可以完成，但不要修改文件或复选框。

若这是修复后的复审，只检查上一轮已确认问题、修复引入的回归、任务验收条件和
新的 P0/P1，不重新进行无边界审查。
```

## 7. Gate 验收 Chat 提示词

在 Gate 的全部前置任务看起来已完成后使用独立 Chat。

```text
只做 <GATE_ID> 的独立验收，不修改任何文件。

读取 AGENTS.md、Plan 中该阶段任务和 <GATE_ID> 条目、Design 中与该 Gate 直接相关的
完成标准和 ADR，以及相关代码、测试和提交证据。

逐个 Gate 条目标记：
- 通过：有直接且充分的证据
- 失败：实现或行为不满足要求
- 未证明：可能已实现，但验证证据不足
- 不适用：说明本阶段不适用的依据

每项给出文件、测试、命令或提交证据，并汇总：
- 未解决的 P0/P1
- 阻塞项状态
- 跨平台、故障注入或发布验证缺口
- 是否允许进入下一阶段

只有全部强制项通过、没有阻塞 P0/P1 且证据充分时，才能给出“Gate 通过”。
缺失工作优先映射回现有任务；若现有任务无法承载，指出需要用户确认后修改 Plan，
不得自行扩大任务。
```

## 8. 设计问题与变更控制

实施或 Review 中遇到以下情况必须暂停当前任务：

- Design 与代码或平台事实矛盾；
- Design 与 Plan 冲突；
- 必须修改架构、协议、职责或兼容性才能继续；
- 当前任务明显遗漏必要工作，且无法在原范围内完成；
- 已完成任务的结论因新证据失效；
- Design 中记录的**当前代码基线**与实际代码不再一致。

最后一条需要单独说明。Design 除了描述目标架构，还显式记录了若干“当前实现是什么样”的
基线事实，例如 Voice 入口现由 Core 持有、不存在集中的媒体目录解析器、`direct_session`
同时绕过 ACL gate 与 TaskTracker、若干 per-channel 硬编码表的位置、以及部分库只是传递
依赖。这些基线是任务范围和工作量估算的依据。`main` 上的 Channel 代码仍在演进，如果发现
基线已经漂移，必须先报告并更新 Design，再继续实施；不得在“目标描述”与“现状描述”之间
自行取舍。

此时先做事实和影响分析，不直接实施新方向：

```text
只分析与 <TASK_ID_OR_GATE> 相关的设计问题，不修改业务代码。

问题：<DESCRIPTION>

读取相关 Design 章节和 ADR、Plan 中受影响任务及 Gate，并检查当前代码和测试以验证
事实。输出：
- 当前设计要求和代码事实
- 冲突或遗漏的直接证据
- 当前任务能否安全继续
- 至少两个可行方案及主要取舍
- 推荐方向及理由
- 受影响的 Design 章节、ADR、任务、依赖和 Gate
- 文档修改和重新验证 checklist

等待用户确认方向。确认后先更新 Design/ADR，再更新 Plan；文档确认前不实施业务代码。
```

重要历史规则：

- 新 ADR 替代旧 ADR 时保留旧记录并标明替代关系；
- 已完成结论失效时按 Plan 使用 `[~]`，不能继续保持 `[x]`；
- 修复使用新提交，不 amend 已完成任务的历史；
- 任务标题和完整任务索引只维护在 Plan，不在本文件复制。

## 9. 提交边界

提交策略以 Plan 和当前用户授权为准。一次提交只包含一个任务或该任务已确认的修复，
不得混入其他任务、无关清理或用户已有改动。初始提交不代表任务完成；独立 Review 和
最终验证通过后才能更新完成状态。
